# 0001：Windows 原生技术路线与模块边界

- 日期：2026-10-17
- 状态：已接受（用户确认 Rust + Win32；模块组织为本次工程搭建方案）
- 关联：`REQUIREMENTS.md` 第 1、3、12 节

## 背景

旧实现基于 Node.js 和 Windows 启动脚本。新版本要求小体积、免安装、原生 GUI、后台运行、单实例、可选登录自启和两种配置路径。

## 决策

1. 使用 Rust + Win32，不使用 Node 套壳、Electron 或 WebView。
2. 首版面向 Windows 10/11 x64，使用单个 Cargo package。
3. 按 `app`、`config`、`proxy`、`windows`、`ui`、`logging` 划分职责。
4. Windows 专属模块使用条件编译；其他平台只服务纯逻辑验证。
5. 当前骨架不添加第三方依赖；实际实施时再选择成熟网络、TLS 和 Windows 绑定库。
6. 保留旧脚本原位作为行为参考，不自动执行、迁移或删除。

后续决策：第6项在用户明确授权的公开清理范围内由 [ADR0011](0011-publication-history-hygiene.md) 取代；其余决策及本记录的当时事实不变。

## 备选方案

- Node.js 打包：复用成本低，但不能消除运行时开销，不符合本次原生方向。
- C++ + Win32：适合极小体积，但并发和内存安全维护成本更高。
- C# 或 WebView 路线：开发便利，但运行时与分发取舍不符合当前优先级。

## 影响与风险

- 需要重新实现并验证代理协议及 Windows 集成，不能只验证 UI 能打开。
- Rust 路线不自动保证体积、性能或绿色分发，需要基准与干净环境验证。
- GUI 与异步网络必须解耦，FFI 需约束句柄所有权和线程访问。
- 软件目录模式与 DPAPI 跨机器便携存在取舍，遵守需求中的显式存储选择。
